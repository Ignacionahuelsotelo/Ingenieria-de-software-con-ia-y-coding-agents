**Base:** `docs/prd.md` §H-004 y §5 casos 4 y 6 · `docs/architecture.md` D-8, D-10
**Depende de:** H-001, H-002, H-003.
**Dueño del código:** @dev

## 1. Contrato

### `DELETE /api/expenses/:id`

Request: sin body.

Response `204 No Content`, **sin body** (D-8).

Efectos: el gasto desaparece de `GET /api/expenses` y los balances se
recalculan como si nunca hubiera existido. El id borrado **no se reutiliza**.

| Situación | HTTP | Body exacto |
|---|---|---|
| el gasto no existe (o ya fue borrado) | 404 | `{"error":"No existe el gasto 'X'","code":"EXPENSE_NOT_FOUND"}` |

### `DELETE /api/people/:id`

Request: sin body.

Response `204 No Content`, **sin body**.

Efectos: la persona desaparece de `GET /api/group`. Solo se permite si **no
aparece en ningún gasto**, ni como `paidBy` ni dentro de `splitBetween`.

| Situación | HTTP | Body exacto |
|---|---|---|
| la persona no existe | 404 | `{"error":"No existe la persona 'X'","code":"PERSON_NOT_FOUND"}` |
| la persona participa de al menos un gasto | 409 | `{"error":"No se puede sacar a 'X' porque participa de 1 o más gastos. Borrá o corregí esos gastos primero","code":"PERSON_IN_USE"}` |

`'X'` es el id literal recibido de la URL, entre comillas simples. El mensaje
del 409 es literal, tal cual está escrito (incluida la frase "1 o más": no se
calcula la cantidad real).

**Orden de chequeo en `DELETE /api/people/:id`:** existencia primero (404),
uso después (409). Una persona inexistente nunca devuelve 409.

**Invariante después de cualquier borrado:** la suma de todos los
`balanceCents` de `GET /api/balances` es exactamente `0`.

## 3. Implementación

**Paso 1 — semillas como constantes en `backend/src/store.js`.** Como ahora se
pueden borrar semillas, `_reset()` tiene que poder **reconstruirlas**. Reemplazar
la inicialización actual por una que parta de constantes, manteniendo los mismos
datos exactos:

```js
const SEED_PEOPLE = [
  { id: "ana", name: "Ana" },
  { id: "beto", name: "Beto" },
  { id: "caro", name: "Caro" },
];

const SEED_EXPENSES = [
  { id: "e1", description: "Cabaña", amountCents: 120000, paidBy: "ana", splitBetween: ["ana", "beto", "caro"] },
  { id: "e2", description: "Nafta", amountCents: 45000, paidBy: "beto", splitBetween: ["ana", "beto", "caro"] },
  { id: "e3", description: "Asado", amountCents: 33000, paidBy: "caro", splitBetween: ["ana", "caro"] },
];

const people = new Map();
const expenses = new Map();
let nextId = 4;
let nextPersonId = 1;

function seed() {
  people.clear();
  expenses.clear();
  for (const p of SEED_PEOPLE) people.set(p.id, { ...p });
  for (const e of SEED_EXPENSES) expenses.set(e.id, { ...e, splitBetween: [...e.splitBetween] });
  nextId = 4;
  nextPersonId = 1;
}

seed();
```

Y `_reset()` pasa a ser `_reset() { seed(); }`. Las copias (`{ ...p }`,
`[...e.splitBetween]`) son obligatorias: sin ellas un test podría mutar la
semilla y contaminar a los demás.

**Paso 2 — métodos nuevos del store:**

```js
hasExpense: (id) => expenses.has(id),

removeExpense(id) {
  return expenses.delete(id);   // true si existía
},

removePerson(id) {
  return people.delete(id);     // true si existía
},

/** true si la persona aparece en algún gasto, como pagador o en el reparto. */
isPersonUsed(id) {
  for (const e of expenses.values()) {
    if (e.paidBy === id || e.splitBetween.includes(id)) return true;
  }
  return false;
},
```

**Paso 3 — `DELETE` en `backend/src/routes/expenses.js`:**

```js
expensesRouter.delete("/:id", (req, res) => {
  const { id } = req.params;
  if (!store.hasExpense(id)) {
    return res.status(404).json({ error: `No existe el gasto '${id}'`, code: "EXPENSE_NOT_FOUND" });
  }
  store.removeExpense(id);
  res.status(204).end();
});
```

**Paso 4 — `DELETE` en `backend/src/routes/people.js`:**

```js
peopleRouter.delete("/:id", (req, res) => {
  const { id } = req.params;
  if (!store.hasPerson(id)) {
    return res.status(404).json({ error: `No existe la persona '${id}'`, code: "PERSON_NOT_FOUND" });
  }
  if (store.isPersonUsed(id)) {
    return res.status(409).json({
      error: `No se puede sacar a '${id}' porque participa de 1 o más gastos. Borrá o corregí esos gastos primero`,
      code: "PERSON_IN_USE",
    });
  }
  store.removePerson(id);
  res.status(204).end();
});
```

`res.status(204).end()` — nunca `.json()`: un 204 con body es inválido.

## 4. Riesgos

| Riesgo | Plan B |
|---|---|
| Reescribir la inicialización del store rompe los 24 tests existentes. | Los datos semilla son **idénticos** a los actuales. Correr `cd backend && npm test` inmediatamente después del paso 1, antes de escribir las rutas. Si algo se pone rojo, es un error de transcripción de la semilla. |
| Tentación de borrar en cascada los gastos de la persona. | Prohibido (D-10). El 409 es el comportamiento pedido por el PRD. |
| Tentación de hacer "soft delete" con un flag `active`. | Prohibido (D-10). |
| El id borrado se reutiliza por reiniciar el contador. | Los contadores son monótonos y solo se reinician en `_reset()`. No decrementar nunca. |
| Devolver 200 con body en el DELETE porque "el frontend lo necesita". | No lo necesita: el frontend hace `loadAll()` después de mutar (D-12). |

## 5. Tests (`backend/tests/delete.test.js`)

- `DELETE /api/expenses/e2` responde 204 con body vacío.
- Tras borrar `e2`, `GET /api/expenses` devuelve 2 gastos y ninguno tiene id `e2`.
- Tras borrar `e2`, la suma de `balanceCents` de `GET /api/balances` es 0.
- Tras borrar `e2`, los balances coinciden con los de un grupo que solo tuvo `e1` y `e3`.
- `DELETE /api/expenses/e2` dos veces: la segunda responde 404 `EXPENSE_NOT_FOUND`.
- `DELETE /api/expenses/inexistente` responde 404 `EXPENSE_NOT_FOUND` y el mensaje contiene `'inexistente'`.
- Tras un 404 de borrado, `GET /api/expenses` sigue devolviendo 3 gastos.
- Borrar todos los gastos deja `GET /api/expenses` en `[]` y todos los balances en 0.
- Una persona recién agregada (`POST /api/people`) se puede borrar: 204.
- Tras borrarla, `GET /api/group` vuelve a tener 3 personas.
- `DELETE /api/people/ana` responde 409 `PERSON_IN_USE` (participa de `e1`).
- Tras el 409, `GET /api/group` sigue teniendo a `ana`.
- `DELETE /api/people/fantasma` responde 404 `PERSON_NOT_FOUND`, no 409.
- Una persona que solo aparece como `paidBy` (y no en `splitBetween`) también da 409.
- Después de borrar los gastos donde participa `caro`, `DELETE /api/people/caro` responde 204.
- El id de una persona borrada no se reutiliza: tras borrar `p1`, el alta siguiente es `p2`.
- `store._reset()` restaura las 3 personas y los 3 gastos semilla aunque se hayan borrado todos.
