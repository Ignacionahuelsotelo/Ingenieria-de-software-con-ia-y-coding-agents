## 1. Contrato

### `POST /api/expenses`

Request:

```json
{
  "description": "Vino",
  "amountCents": 10000,
  "paidBy": "ana",
  "splitBetween": ["ana", "beto", "caro"]
}
```

Response `201`:

```json
{
  "expense": {
    "id": "e4",
    "description": "Vino",
    "amountCents": 10000,
    "paidBy": "ana",
    "splitBetween": ["ana", "beto", "caro"]
  }
}
```

Reglas del contrato:

- `amountCents` es **entero y > 0**, en centavos. `100.5`, `"10000"`, `0` y
  `-1` se rechazan. `amountCents` en pesos no existe (D-2).
- `description` se guarda trimmeada.
- `paidBy` **puede o no** estar en `splitBetween`. Los dos casos son válidos y
  se calculan distinto (caso borde 2 del PRD). **No** se valida pertenencia.
- `splitBetween` puede tener **una sola** persona (caso borde 9).
- `splitBetween` se guarda **tal cual llega** (mismo orden, sin deduplicar). El
  orden importa: `splitCents` reparte el resto a los primeros de la lista.
- Cargar dos veces el mismo body crea **dos gastos** con ids distintos. La app
  no detecta duplicados (caso borde 6).
- El gasto afecta los balances de inmediato: `GET /api/balances` lo refleja en
  la llamada siguiente.

### Errores

| Situación | HTTP | Body exacto |
|---|---|---|
| `description` ausente / no string / vacía / solo espacios | 400 | `{"error":"La descripción es obligatoria y no puede estar vacía","code":"INVALID_DESCRIPTION"}` |
| `amountCents` ausente, no entero, `NaN`, string, o ≤ 0 | 400 | `{"error":"El monto debe ser un entero de centavos mayor a cero","code":"INVALID_AMOUNT"}` |
| `splitBetween` ausente, no array, vacío, o con algún elemento que no es string | 400 | `{"error":"Hay que indicar al menos una persona entre quienes se divide","code":"INVALID_SPLIT"}` |
| `paidBy` no existe en el grupo | 400 | `{"error":"No existe la persona 'X'","code":"UNKNOWN_PERSON"}` |
| algún id de `splitBetween` no existe | 400 | `{"error":"No existe la persona 'X'","code":"UNKNOWN_PERSON"}` |

`'X'` es el id literal recibido, entre comillas simples.

**Orden de validación (fijo, no negociable):** `description` → `amountCents` →
`splitBetween` (forma) → `paidBy` (existencia) → cada id de `splitBetween`
(existencia, en orden del array). Si hay varios errores se devuelve **el
primero** según ese orden.

En cualquier `400` no se crea nada, no se consume un id de gasto, y
`GET /api/expenses` devuelve exactamente lo mismo que antes.

## 3. Implementación

**Paso 1 — `validateExpense` en `backend/src/domain/validation.js`.** Recibe el
body crudo y un predicado `hasPerson` (inyectado, para que el módulo siga puro y
sin importar el store):

```js
/**
 * @param {any} body
 * @param {(id:string)=>boolean} hasPerson
 * @returns {{ok:true, value:{description,amountCents,paidBy,splitBetween}}
 *          | {ok:false, code:string, message:string}}
 */
export function validateExpense(body, hasPerson) {
  const b = body ?? {};

  if (typeof b.description !== "string" || b.description.trim() === "") {
    return { ok: false, code: "INVALID_DESCRIPTION", message: "La descripción es obligatoria y no puede estar vacía" };
  }
  if (!Number.isInteger(b.amountCents) || b.amountCents <= 0) {
    return { ok: false, code: "INVALID_AMOUNT", message: "El monto debe ser un entero de centavos mayor a cero" };
  }
  if (!Array.isArray(b.splitBetween) || b.splitBetween.length === 0 || b.splitBetween.some((id) => typeof id !== "string")) {
    return { ok: false, code: "INVALID_SPLIT", message: "Hay que indicar al menos una persona entre quienes se divide" };
  }
  if (typeof b.paidBy !== "string" || !hasPerson(b.paidBy)) {
    return { ok: false, code: "UNKNOWN_PERSON", message: `No existe la persona '${b.paidBy}'` };
  }
  for (const id of b.splitBetween) {
    if (!hasPerson(id)) {
      return { ok: false, code: "UNKNOWN_PERSON", message: `No existe la persona '${id}'` };
    }
  }

  return {
    ok: true,
    value: {
      description: b.description.trim(),
      amountCents: b.amountCents,
      paidBy: b.paidBy,
      splitBetween: [...b.splitBetween],
    },
  };
}
```

`Number.isInteger` cubre de una sola vez: ausente, `null`, string, `NaN`,
`Infinity` y decimales. No agregar más chequeos.

**Paso 2 — el `POST` en `backend/src/routes/expenses.js`**, debajo del `GET`
existente:

```js
expensesRouter.post("/", (req, res) => {
  const check = validateExpense(req.body, (id) => store.hasPerson(id));
  if (!check.ok) return res.status(400).json({ error: check.message, code: check.code });
  const expense = store.addExpense(check.value);
  res.status(201).json({ expense });
});
```

## 4. Riesgos

| Riesgo | Plan B |
|---|---|
| Alguien "mejora" el producto exigiendo que `paidBy` esté en `splitBetween`. | Prohibido explícitamente (caso borde 2). Hay un test que carga un gasto con `paidBy` fuera del reparto y espera 201. |
| Deduplicar o reordenar `splitBetween`. | Prohibido: cambia a quién le toca el centavo sobrante y vuelve el resultado no reproducible. Se guarda tal cual. |
| El frontend manda pesos y el server los toma como centavos. | El contrato es centavos, punto. La conversión vive solo en `frontend/app.js` (D-3, H-006). |
| Duplicar validación con `tools/handlers.js`. | Es una decisión tomada (D-6). No refactorizar `handlers.js`. |
| `splitBetween` con ids repetidos (`["ana","ana"]`). | Es válido y se acepta: significa doble porción. `computeBalances` lo maneja restando dos veces. No se rechaza. |

## 5. Tests (`backend/tests/expenses.test.js`)

- `POST /api/expenses` válido responde 201 y devuelve el gasto con id `e4`.
- El gasto creado aparece en `GET /api/expenses` (pasa de 3 a 4).
- La descripción se guarda trimmeada.
- `paidBy` fuera de `splitBetween` es válido: responde 201.
- `splitBetween` con una sola persona es válido: responde 201.
- Dos `POST` idénticos crean dos gastos con ids distintos (`e4` y `e5`).
- Un monto que no divide exacto (`100` entre 3) reparte `[34,33,33]`: la suma de las partes de `splitCents(100,3)` es 100 y `GET /api/balances` sigue sumando 0.
- `description: ""` → 400 `INVALID_DESCRIPTION`.
- `description` ausente → 400 `INVALID_DESCRIPTION`.
- `amountCents: 0` → 400 `INVALID_AMOUNT`.
- `amountCents: -500` → 400 `INVALID_AMOUNT`.
- `amountCents: 100.5` → 400 `INVALID_AMOUNT`.
- `amountCents: "1000"` → 400 `INVALID_AMOUNT`.
- `splitBetween: []` → 400 `INVALID_SPLIT`.
- `splitBetween` ausente → 400 `INVALID_SPLIT`.
- `splitBetween: "ana"` (no array) → 400 `INVALID_SPLIT`.
- `paidBy: "nadie"` → 400 `UNKNOWN_PERSON` con mensaje que contiene `'nadie'`.
- `splitBetween: ["ana","fantasma"]` → 400 `UNKNOWN_PERSON` con mensaje que contiene `'fantasma'`.
- Tras cualquier 400, `GET /api/expenses` sigue devolviendo 3 gastos.
- Tras un 400, el siguiente alta válida obtiene id `e4` (el rechazo no consumió id).
- Una persona agregada por `POST /api/people` puede ser `paidBy` de un gasto nuevo.
