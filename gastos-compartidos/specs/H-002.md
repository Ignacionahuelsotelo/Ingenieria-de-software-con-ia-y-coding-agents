# H-002 — Agregar una persona al grupo

**Base:** `docs/prd.md` §H-002 · `docs/architecture.md` §4, D-5, D-7
**Depende de:** H-001 (`app.js` ya monta routers).
**Dueño del código:** @dev

---

## 1. Contrato

### `POST /api/people`

Request:

```json
{ "name": "Dani" }
```

Response `201`:

```json
{ "person": { "id": "p1", "name": "Dani" } }
```

- El `name` se guarda **trimmeado**: `"  Dani  "` se guarda como `"Dani"`.
- El id es `p` + contador (`p1`, `p2`, …). Nunca se reutiliza dentro de la vida
  del proceso.
- Se permiten nombres repetidos: dos `POST` con `{"name":"Juan"}` crean dos
  personas distintas (`p1` y `p2`), ambas con `name: "Juan"`.
- Agregar una persona **no** modifica ningún gasto. Su balance queda en `0`.

### Errores

| Situación | HTTP | Body exacto |
|---|---|---|
| `name` ausente | 400 | `{"error":"El nombre es obligatorio y no puede estar vacío","code":"INVALID_NAME"}` |
| `name` no es string (`123`, `null`, `{}`, array) | 400 | `{"error":"El nombre es obligatorio y no puede estar vacío","code":"INVALID_NAME"}` |
| `name` vacío o solo espacios (`""`, `"   "`) | 400 | `{"error":"El nombre es obligatorio y no puede estar vacío","code":"INVALID_NAME"}` |
| body ausente por completo | 400 | `{"error":"El nombre es obligatorio y no puede estar vacío","code":"INVALID_NAME"}` |

En cualquier `400`, el grupo queda **exactamente igual que antes**: mismo número
de personas, mismo contador de ids (un rechazo **no** consume un id).

## 3. Implementación

**Paso 1 — `backend/src/domain/validation.js`.** Funciones puras, sin Express y
sin importar el store. Devuelven un resultado, **no lanzan**:

```js
/** @returns {{ok:true, value:string} | {ok:false, code:string, message:string}} */
export function validateName(raw) {
  if (typeof raw !== "string" || raw.trim() === "") {
    return {
      ok: false,
      code: "INVALID_NAME",
      message: "El nombre es obligatorio y no puede estar vacío",
    };
  }
  return { ok: true, value: raw.trim() };
}
```

**Paso 2 — `backend/src/store.js`.** Agregar el contador y el método. **No
cambiar las semillas ni los ids existentes.**

```js
let nextPersonId = 1;

// dentro de export const store = { ... }
addPerson({ name }) {
  const id = `p${nextPersonId++}`;
  const person = { id, name };
  people.set(id, person);
  return person;
},
```

Extender `_reset()` para que además de los gastos restaure las personas
semilla y ambos contadores:

```js
_reset() {
  for (const id of [...expenses.keys()]) if (!["e1", "e2", "e3"].includes(id)) expenses.delete(id);
  for (const id of [...people.keys()]) if (!["ana", "beto", "caro"].includes(id)) people.delete(id);
  nextId = 4;
  nextPersonId = 1;
},
```

> `_reset()` **no** vuelve a crear entradas borradas de las semillas; eso se
> completa en H-004, que sí borra personas y gastos. En H-002 alcanza con lo de
> arriba.

**Paso 3 — `backend/src/routes/people.js`:**

```js
import { Router } from "express";
import { store } from "../store.js";
import { validateName } from "../domain/validation.js";

export const peopleRouter = Router();

peopleRouter.post("/", (req, res) => {
  const check = validateName(req.body?.name);
  if (!check.ok) return res.status(400).json({ error: check.message, code: check.code });
  const person = store.addPerson({ name: check.value });
  res.status(201).json({ person });
});
```

**Paso 4 — `backend/src/app.js`:** `app.use("/api/people", peopleRouter);`

**Paso 5 — tests.** Usar `beforeEach(() => store._reset())` en
`backend/tests/people.test.js` para que los ids sean predecibles.

## 4. Riesgos

| Riesgo | Plan B |
|---|---|
| `req.body` es `undefined` si no se manda `Content-Type: application/json`. | Ya está cubierto: `req.body?.name` → `undefined` → `INVALID_NAME` 400. Hay un test para eso. |
| Los tests que corren en el mismo proceso comparten el store y se contaminan entre sí. | `beforeEach(() => store._reset())` en todo test que agregue personas. Obligatorio. |
| Extender `_reset()` rompe los 24 tests existentes. | `_reset()` sigue siendo idempotente y las semillas quedan intactas; si algo se pone rojo, revertir el cambio de `_reset` y anotarlo en el log. Correr `npm test` antes de seguir. |
| Un dev "arregla" nombres duplicados rechazándolos. | Prohibido: el PRD exige permitir dos Juanes. |

## 5. Tests (`backend/tests/people.test.js`)

- `POST /api/people` con `{"name":"Dani"}` responde 201.
- La respuesta es `{ person: { id: "p1", name: "Dani" } }` tras `_reset()`.
- Después del alta, `GET /api/group` devuelve 4 personas e incluye a `Dani`.
- El nombre se guarda trimmeado: `{"name":"  Dani  "}` → `person.name === "Dani"`.
- Dos altas seguidas devuelven ids distintos (`p1` y `p2`).
- Dos personas con el mismo `name` conviven y se distinguen por `id`.
- `{"name":""}` responde 400 con `code === "INVALID_NAME"`.
- `{"name":"   "}` responde 400 con `code === "INVALID_NAME"`.
- `{}` responde 400 con `code === "INVALID_NAME"`.
- `{"name":123}` responde 400 con `code === "INVALID_NAME"`.
- Tras un 400, `GET /api/group` sigue devolviendo la misma cantidad de personas.
- Tras un 400, el siguiente alta válida obtiene `p1` (el rechazo no consumió id).
- Agregar una persona no cambia la cantidad de gastos (`GET /api/expenses` sigue en 3).
