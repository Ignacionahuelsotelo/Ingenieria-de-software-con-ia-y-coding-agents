Los cuatro proyectos que construimos, qué pieza de harness aportó cada uno, y qué hacer con eso en un repo propio.

00 · Encuadre

El objeto de estudio no fue la herramienta

Fue el harness: el contexto, las herramientas, los permisos y las verificaciones que rodean al modelo.

modelo ← se reemplaza cada pocos meses ┌─────────────────────────────┐ │ contexto · herramientas │ ← lo construís vos, │ permisos · verificación │ y decide el resultado └─────────────────────────────┘

Dos personas con el mismo modelo obtienen resultados distintos según lo que le pusieron alrededor. Esa diferencia es el tema del curso.

02 · Proyecto 1

fútbol — consumir un MCP

Qué hicimos

  • Conectamos el MCP de SportDB con un comando y lo dejamos en .mcp.json, versionado
  • Un subagente exploró la API tool por tool y escribió docs/sportdb-api.md
  • De ese documento salió una skill con los ids de liga y los formatos de fecha
  • Un hook en el evento Stop bloquea el turno si falta el test de una ruta

Qué dejó cada decisión

  • El subagente corre en su propia ventana de contexto. Hizo 20 llamadas y trajo megabytes de JSON; a la sesión principal volvieron diez líneas
  • Devuelve un resumen, no todo lo que vio. Por eso el subagente escribe un archivo: es el único lugar donde el detalle sobrevive
  • El hook no escribe el test. Se niega a terminar el turno hasta que exista
03 · Proyecto 2

turnos — spec-driven development

constitution → specify → clarify → plan → tasks → analyze → implement → converge
clarify

Hace hasta cinco preguntas sobre lo que quedó ambiguo y escribe las respuestas de vuelta en el spec. Sobre "un sistema de turnos" salieron seis decisiones sin tomar: anticipación mínima, doble reserva, plazo de cancelación.

analyze

Compara spec, plan y tareas entre sí. En nuestra corrida encontró siete tareas apuntando a un directorio que el plan declaraba eliminado — antes de escribir una línea de código.

converge

Después de implementar, compara el código contra el spec original y genera las tareas de lo que quedó afuera. Sin este paso el pipeline termina cuando alguien dice "listo".

Las tres fases opcionales son justamente las que un pipeline casero no tiene. Existen porque son los tres puntos donde el método falla en la práctica.

04 · Proyecto 3

gastos — cinco agentes coordinados

RolDueño deNo puede

Lo que los convierte en equipo no es la cantidad, sino que cada uno tenga un entregable, un permiso y un límite.

Ningún agente le habla a otro: dejan estado en un tablero editable y una bitácora append-only. Es una arquitectura de pizarrón — un patrón de los años 70 que funciona acá porque cada agente corre en su propio contexto y no sabe que los demás existen.

05 · Proyecto 4

sismos — construir el servidor

Las tres primitivas

  • Tools — las invoca el modelo
  • Resources — los lee la aplicación, por URI
  • Prompts — los elige el usuario

La diferencia entre las tres es quién dispara.

Las tres fuentes

  • API pública sin key (USGS)
  • Base local (SQLite)
  • Un modelo abierto, dentro de dos tools

Una sola tool, informe_watchlist, encadena las tres.

Y un cliente propio

  • La entrada es lenguaje natural
  • Un modelo abierto elige qué tool llamar
  • Sin Claude en ningún punto del camino

El servidor MCP no orquesta: expone capacidades. El modelo que decide vive del lado del cliente — por eso el mismo servidor funciona con cualquier modelo.

07 · Contexto

Qué darle al modelo, y dónde ponerlo

1

Dale contexto, no solo órdenes

Para quién es el producto, qué convenciones sigue el repo, qué restricciones hay y por qué. Eso el modelo no lo puede deducir del código: es lo único que solo sabés vos.

2

Siempre vs. cuando aplica

Si vale para todo el proyecto, va en CLAUDE.md y se carga en cada request. Si vale para una tarea puntual, va en una skill — así no pagás su costo de contexto cuando no la necesitás.

3

Documento largo, regla corta

El documento de referencia se consulta cuando hace falta. La skill es corta y se activa sola. Que la skill remita al documento en vez de copiarlo: si no, cuando actualizás uno el otro queda mintiendo.

4

El estado vive en archivos

No en la memoria de la sesión. Por eso podés cerrar la terminal, cambiar de modelo o de herramienta y retomar donde estabas — y por eso todo esto se revisa en un pull request.

08 · Instrucciones · 1 de 3

Decí cuándo se usa, no solo qué hace

La descripción de una tool o una skill no es documentación: es el criterio de activación. Es lo que el modelo lee para decidir si la usa.

Descripción que no activa bien

"Busca sismos en la base del USGS filtrando por región y magnitud."

Correcta y completa. Pero solo describe la mecánica: el modelo tiene que inferir cuándo le sirve.

La que usamos

"Busca sismos en la base del USGS filtrando por región, magnitud mínima y ventana de días. Es la tool principal: usala para '¿hubo sismos en X?', '¿tembló fuerte esta semana?' o cualquier consulta sobre actividad sísmica reciente."

Lo mismo aplica al description de una skill: "Usar SIEMPRE que se escriba código que llame una tool mcp__sismos__*" activa; "Documentación del MCP de sismos" no.

09 · Instrucciones · 2 de 3

Reemplazá cada adjetivo por algo verificable

Los adjetivos describen un resultado en vez de elegirlo. Todo proyecto que pide "moderno y limpio" recibe la misma página.

Brief de diseño vago

"Un frontend moderno, limpio y minimalista para la app de resultados."

Resultado: fondo crema, serif de alto contraste, acento terracota. La estética a la que converge todo output generado hoy.

El que usamos

"Referencia: los teletextos de resultados de los 80, con marcadores monoespaciados sobre bloques sólidos de color. Restricción dura: cero border-radius y cero sombras. No usar: gradientes, glassmorphism, acento violeta."

Tres partes: un referente concreto del mundo del tema, una restricción dura que fuerza a resolverlo de otra manera, y una lista de prohibidos con los defaults del modelo. La misma estructura sirve para código: en vez de "hacelo robusto", "toda ruta nueva necesita su test en backend/tests/".

10 · Instrucciones · 3 de 3

Cerrá el alcance y el formato de salida

Lista cerrada de archivos

En los specs del proyecto de turnos, cada uno lleva una tabla de archivos a crear o modificar, seguida de una línea literal:

No crear ningún otro archivo. No tocar frontend/.

Sin eso, el agente "aprovecha" y refactoriza de paso. Con eso, git status se compara contra la tabla y el desvío se ve solo.

Criterios verificables con un comando

Comparados con los que suenan bien y no significan nada:

✓ npm test pasa ✓ POST /api/ask responde 200 con {answer} ✓ git status no muestra cambios en frontend/ ✗ el código queda limpio ✗ buen manejo de errores

Y pedí un artefacto que solo se produce siendo riguroso

El agente revisor del curso exige, por cada hallazgo, un campo "Cómo falla" con un input concreto que rompa el código, más la regla: "si no podés escribir ese input, no es un hallazgo: borralo". Un modelo al que le pedís "revisá" siempre encuentra algo — quiere ser útil. Forzarlo a demostrar la falla elimina los hallazgos inventados sin pedirle que "sea riguroso".

11 · Instrucciones

Lo que dejó de funcionar

Estas técnicas se escribieron para modelos que desobedecían. Con los modelos actuales empeoran el resultado, no lo mejoran.

Énfasis inflado

CRITICAL: You MUST use this tool…

Hoy la tool se dispara de más — se documentó el caso de modelos buscando en la web para responder una cuenta simple. La forma correcta es "Usá esta tool cuando…".

Pedir verificación

"Revisá tu trabajo antes de responder"

Los modelos actuales ya verifican solos. La instrucción produce sobre-verificación: pasos redundantes y más tokens. Anthropic recomienda borrarla, no reescribirla.

Guionar el juicio

"PASO 1… PASO 2… PASO 3…"

Para tareas de criterio, el plan del modelo suele ser mejor que el guion escrito a mano. Describí el resultado y las restricciones. Guioná solo lo frágil: comandos destructivos, flujos de auth.

Sobrecargar el rol

"Sos un experto senior con 20 años…"

Una línea de rol está bien. El problema es cuando reemplaza al contexto real: qué producto, qué público, qué nivel de calidad. Sé explícito sobre la perspectiva que querés.

Fuentes: Prompt engineering best practices — Anthropic ("menos andamiaje, más curación"; XML y role prompting ya no hacen falta) · Migration guide — Anthropic (secciones Prompt-Behavior Changes de cada modelo, con las tablas antes/después).

13 · Permisos

Cuando el agente actúa fuera del repo

Ejemplo del curso: el revisor pasa de escribir un archivo a abrir issues en GitHub. Ahí aparecen tres preguntas que antes no existían.

¿Qué pasa si corre dos veces?

Si el revisor se ejecuta de nuevo sobre el mismo diff, abre los mismos issues duplicados. Solución: antes de crear, listar los issues abiertos y comparar. Sin ese paso, cada corrida ensucia el repositorio.

¿Cuál es el peor caso?

Si el modelo se entusiasma y encuentra treinta hallazgos, abre treinta issues. Solución: un tope duro escrito en el agente — máximo 8 por corrida, y solo los de severidad alta. El resto queda en el archivo.

¿Cuánto cuesta deshacerlo?

Cerrar un issue de más lleva un click. Un git push --force o un mail enviado, no. Regla: el agente puede hacer lo que sea barato de revertir; todo lo demás pasa por vos.

Las tres respuestas se escriben en el prompt del agente. Son instrucciones en lenguaje natural, o sea probabilísticas — si el riesgo es alto, la versión dura es un hook que intercepte el comando antes de que se ejecute.

14 · Control

Un error devuelto es información; uno lanzado corta la conversación

Cuando una tool falla, tenés dos opciones — y la diferencia cambia lo que puede hacer el agente después.

Lanzar la excepción
throw new Error( "Región 'españa' desconocida" );

La excepción sube por el servidor, la conversación se corta con un error. El modelo nunca se entera de qué pasó ni puede corregirse.

Devolverlo como resultado
return { content: "Error: región 'españa' desconocida. Usá sismo_listar_regiones.", isError: true };

El modelo lee ese texto como el resultado de la tool, llama a sismo_listar_regiones, y sigue. En la demo lo vimos recuperarse solo.

De ahí que el mensaje de error importe tanto como la descripción de la tool: es texto que un modelo va a leer para decidir su próximo paso. Un "fetch failed" no le dice nada; "no hay servidor MCP en :8787, corré npm run dev" sí.

15 · Control

Quién juzga y quién bloquea son roles distintos

El servicio de Code Review de Anthropic revisa un pull request con varios agentes, marca los hallazgos inline… y su check siempre termina en estado neutral. Nunca bloquea un merge.

Agentes revisan → publican los hallazgos con su severidad │ ▼ tu CI lee el conteo y decide si frena el merge

La documentación es explícita: si querés que los hallazgos bloqueen, tenés que leer el resumen de severidad en tu propio pipeline. Te dan hasta el comando: un gh api … | jq que devuelve {"normal": 2, "nit": 1}.

Es el mismo patrón que ya habíamos escrito a mano en el hook de tests: el agente produce un juicio, una capa determinística decide qué hacer con él. Ni Anthropic le da a su propio revisor la autoridad de frenar un merge.

Fuente: Code Review — Claude Code docs, sección Check run output.

16 · Método

Cuando sale mal, corregí la entrada

escribís la entrada → el agente produce → mirás el resultado ↑ │ └────────── ¿salió mal? ─────────────────────┘ corregí la ENTRADA, no la salida

Eligió mal la tool

La descripción dice qué hace pero no cuándo usarla.

Se fue de alcance

El spec no tenía lista cerrada de archivos.

El diseño salió genérico

Le diste adjetivos en vez de un referente y una restricción.

Se saltea un paso

Falta la línea del system prompt que lo obliga a hacerlo.

Parchear la salida a mano resuelve ese caso y deja el problema intacto para el siguiente. Corregir la entrada lo resuelve para siempre — y queda versionado en el repo.

20 · Qué no vimos

Los cuatro temas que siguen

1

Paralelismo

Git worktrees: varias sesiones sobre el mismo repo, cada una en su branch, sin pisarse. El límite práctico está en cuántos diffs podés revisar, no en cuántos agentes podés lanzar.

2

Seguridad del agente

Prompt injection: un README, un issue o una dependencia con instrucciones dirigidas al agente. No se previene en el modelo — se contiene en la ejecución: sandbox, red restringida, variables de entorno limpias.

3

Agentes sin terminal

Correr un agente en CI o de madrugada, sin nadie mirando. Cambia el diseño: no puede preguntar nada, y todo lo que produzca tiene que ser verificable automáticamente.

4

Medir el harness

¿Esa skill mejoró algo? Sin medición, cada cambio es fe. El primer paso es contar tokens y tiempo por tarea antes y después — no hace falta una plataforma para eso.

21 · Panorama

Dónde está el campo en 2026

El mercado se partió en cinco categorías

  • IDEs con IA — Cursor, Windsurf
  • Agentes de terminal — Claude Code, Codex, Gemini/Antigravity
  • Agentes en la nube — corren sin tu máquina
  • Agentes nativos de GitHub — viven en el PR
  • Open source y local — OpenCode, modelos propios

Lo nuevo de este año

  • ADEs — entornos hechos para orquestar varios agentes en paralelo, en vez de un editor con IA agregada
  • Un modelo por tarea — los equipos dejaron de elegir uno solo: caro para planificar, barato para ejecutar en paralelo
  • "Harness engineering" ya es un término con papers y listas curadas propias

El dato que ordena la discusión

96,4% de las organizaciones que hacen software usan herramientas de IA para programar (GitKraken, State of AI in Engineering 2026). Y según el reporte de Anthropic de este año, los equipos que usan agentes reportan una baja moderada del tiempo por tarea y un aumento mucho mayor del volumen de trabajo entregado. La adopción dejó de ser la pregunta; el cuello de botella se corrió a la revisión.

23 · Por dónde empezar

Cinco pasos sobre un repo real

1 · una tarde

Escribí el archivo de instrucciones

Con la herramienta que uses: CLAUDE.md, AGENTS.md o el que corresponda. Poné las tres o cuatro cosas que hoy repetís en cada prompt: stack, convenciones, qué no tocar. Empezá corto y agregá cuando te encuentres repitiendo algo.

2 · una tarde

Extraé una skill de trabajo real

Elegí lo que más repetís. Hacé la tarea a mano una vez, y recién ahí destilá las reglas que seguiste. Una skill inventada de cero sale genérica; una extraída de código que ya funciona, no.

3 · una hora

Convertí una regla en un hook

Tomá una del archivo de instrucciones que se cumple "casi siempre" y hacela obligatoria. Los tests son el mejor primer caso: un script que verifica y devuelve error si falta algo. Es el paso donde se entiende la diferencia entre pedir y garantizar.

4 · una tarde

Un agente que no escriba código

Un revisor o un explorador. Dale las herramientas justas para leer y ninguna para escribir en el código. Es donde el permiso mínimo se entiende sin explicación.

5 · permanente

Commiteá todo eso y revisalo en un PR

Instrucciones, skills, agentes y hooks son código fuente: se versionan, se revisan y viajan con el proyecto. Si están solo en tu máquina, el equipo no los tiene — y vos los perdés cuando cambies de computadora.

Escribir menos código a mano no bajó el listón: lo subió. Si el costo de producir se derrumbó, lo que queda para diferenciar un trabajo de otro es el criterio — qué se construye, con qué límites, y cómo se verifica que esté bien.

Y eso es exactamente lo que no se delega. Un agente ejecuta bien lo que está bien especificado; no sabe si valía la pena hacerlo, ni cuál es el costo de equivocarse en tu dominio. Ahí sigue haciendo falta alguien que entienda el problema.

25 · Última
La discusión sobre si conviene usarla ya terminó.
La que queda es si la vas a usar con harness o sin él.

Sin harness

El agente te acelera y te deja un repo que nadie entiende: código que nadie especificó, convenciones que se cumplen a veces, y una deuda que aparece dos meses después.

Con harness

El mismo agente, la misma velocidad, pero con el contexto escrito, los permisos acotados y las verificaciones corriendo solas. La diferencia no la hace el modelo: la hacen los archivos que pusiste alrededor.

Todo lo que vimos son archivos de texto en el repo. Un MCP es cinco líneas de JSON; un agente, una skill y un hook son markdown y bash. Nada de eso requiere permiso de nadie para empezar.

Lo que aprendieron no es una herramienta puntual — esa va a cambiar. Es cómo se le da forma al trabajo de un sistema que produce mucho más rápido de lo que uno puede revisar.
