Spec-Driven
Development

Escribir la especificación primero, y dejar que el agente la ejecute. Qué es, qué cuesta, y cuándo no vale la pena.

01 · El problema

Los agentes no fallan por no saber escribir código

Fallan por ambigüedad.

Lo que pedís

"Agregá un sistema de turnos para la barbería."

Lo que no dijiste

¿Se puede reservar para dentro de 5 minutos? ¿Qué pasa si dos personas toman el mismo horario a la vez? ¿Hasta cuándo se cancela? ¿Feriados?

Lo que pasa

El agente decide por vos, en silencio, y vos te enterás tres semanas después.

02 · La inversión

El spec es el artefacto. El código es su salida.

conversacional prompt → código → corregir → corregir → corregir spec-driven spec → [ revisión humana ] → código → verificar ↑ │ └──────── si falló, se arregla el SPEC ──────┘

Todo el pensamiento se mueve río arriba. En vez de corregir la salida, definís bien la entrada.

03 · Anatomía

Qué tiene un spec que sirve

Contrato

Inputs y outputs literales, con JSON de ejemplo. No descritos: escritos.

Archivos

Lista cerrada de qué se crea y qué se modifica, más la frase "no crear ningún otro archivo".

Aceptación

Cada criterio se verifica con un comando. "El código queda limpio" no es un criterio.

Riesgos

Qué puede fallar y cuál es el plan B, decidido antes de empezar.

04 · La regla
Cuando la implementación sale mal,
el bug está en el spec.

Si parcheás el código a mano, tapaste el problema y la próxima feature falla igual. Arreglás el spec y volvés a ejecutar.

Es la misma lógica que arreglar el prompt en vez de la respuesta — pero con un artefacto versionado que se revisa en un pull request.

05 · El pipeline

Open source, gratis, y agnóstico de agente: Claude Code, Copilot, Cursor, Gemini, OpenCode y 30 más.

06 · Las tres fases que nadie improvisa

Dónde falla el spec-driven casero

clarify

Una fase obligatoria para encontrar lo sub-especificado. La diferencia entre "ojalá pregunte" y "tiene que preguntar".

analyze

Consistencia entre artefactos. El spec dice una cosa, las tareas dicen otra, y nadie lo nota hasta que el código está escrito.

converge

Compara el código contra el spec original y genera lo que falta. Sin esto, el pipeline termina cuando alguien dice "listo".

08 · Costos

Qué te cuesta

Tiempo

La primera hora no produce una línea de código. Para tareas chicas eso es pérdida neta.

Tokens

Cada fase es una corrida del agente. El pipeline entero cuesta más tokens que pedir el código directo — se recupera solo si evita rehacer trabajo.

Disciplina

Funciona si el equipo respeta el gate. El día que alguien parchea el código sin tocar el spec, los artefactos empiezan a mentir.

Rigidez

Cuando no sabés todavía qué querés construir, escribir un spec es fijar decisiones que no estás listo para tomar.

09 · Criterio

Cuándo sí y cuándo no

Usalo
  • La tarea toca varios archivos
  • Hay un contrato que respetar
  • Lo vas a delegar a un agente
  • El costo de equivocarse es alto
  • Más de una persona toca el código
No lo uses
  • Cambios de una línea
  • Estás explorando, no construyendo
  • Prototipos descartables
  • Todavía no sabés cómo va a quedar

Escribir un spec para renombrar una variable es burocracia, no metodología.

11 · Nuestro caso

Turnos para una barbería

Un pedido de dos líneas que esconde diez decisiones.

/speckit-constitution → principios: test-first, UTC, sin DB, dominio puro /speckit-specify → "el dueño configura horarios, el cliente reserva" /speckit-clarify → ¿reserva con 5 min? ¿doble reserva? ¿cancelación? /speckit-plan → Express + ESM, Map en memoria, Vitest /speckit-tasks → H-001 … H-006 /speckit-analyze → ¿alguna tarea cubre la cancelación del spec? /speckit-implement → código /speckit-converge → qué quedó sin hacer

Cada fase lee del disco lo que la anterior escribió. Podés cerrar la sesión entre una y otra: el estado no vive en el contexto.

12 · Para llevarse
Un spec es un contrato con una máquina que lee literalmente.
  • El spec-driven no es documentación: es la entrada del sistema.
  • La fase de clarify no agrega preguntas — las adelanta.
  • Si el criterio de aceptación no se verifica con un comando, no es un criterio.
  • Cuando falla, se arregla el spec. Nunca el código a mano.
  • GitHub distribuye su metodología oficial como diez archivos markdown. El formato que ya conocés.
