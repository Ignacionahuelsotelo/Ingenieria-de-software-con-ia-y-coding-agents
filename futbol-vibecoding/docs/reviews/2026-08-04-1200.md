### [I1] `getMatchById` aborta la búsqueda completa si una sola liga falla, a diferencia de `getMatchesByDate`
**Archivo:** backend/src/services/sportdb.js:183-195
**Qué pasa:** `findMatchWithLeague` recorre `LEAGUES` secuencialmente y llama `await getLeagueMatches(league)` sin try/catch por liga. `getMatchesByDate` (líneas 167-181), en cambio, envuelve cada liga en try/catch y sigue con las demás si una falla.
**Cómo falla:** Un partido de `europa-league` (última liga del array `LEAGUES` en `config/leagues.js`) existe y sería encontrado, pero si la llamada MCP para `champions-league` (liga anterior en el array) falla de forma transitoria (timeout, error del MCP), `findMatchWithLeague` lanza antes de llegar a `europa-league`. El endpoint `GET /api/matches/:id` devuelve 502 en vez de 200, aunque el partido exista y sea recuperable. Además no hay test que cubra este escenario (solo se testea "no encontrado en ninguna liga", no "falla en una liga intermedia").
**Sugerencia:** Aplicar el mismo patrón try/catch-and-continue que ya usa `getMatchesByDate`, o al menos loguear y continuar con la siguiente liga en vez de propagar el error inmediatamente.

### [I2] `toScore` no maneja score como string vacío, solo `undefined`/`null`
**Archivo:** backend/src/services/sportdb.js:120-122
**Qué pasa:** `toScore` devuelve `null` solo si el valor es `undefined` o `null`; cualquier otro valor se pasa a `Number(...)`.
**Cómo falla:** Si SportDB devuelve `homeScore: ""` para un partido `SCHEDULED` (patrón común en APIs de este tipo para "todavía sin dato", visto también en otros campos como `incidentCommentary` que sí vienen como `""`), `Number("")` es `0`, no `NaN`. El partido upcoming terminaría mostrando `score: { home: 0, away: 0 }` en vez de `null`/`null`, indistinguible de un 0-0 real. No hay ningún test que ejercite un fixture `SCHEDULED` con score vacío para esta función.
**Sugerencia:** Tratar `""` (y valores no numéricos) igual que `undefined`/`null` en `toScore`, devolviendo `null` explícitamente para status `upcoming`.

### [I3] Las rutas nuevas de detalle de partido no tienen test de error (502), solo happy path
**Archivo:** backend/tests/matches.test.js:182 (`/:id/events`), 217 (`/:id/lineups`), 238 (`/:id/statistics`)
**Qué pasa:** A diferencia de `GET /api/matches` (línea 15+), `GET /api/matches?date=` y `GET /api/matches/river-boca` (que sí tienen su test "returns 502 when the SportDB MCP call fails"), los tres describes de `/:id/events`, `/:id/lineups` y `/:id/statistics` solo cubren el caso feliz.
**Cómo falla:** No es un bug de producción, pero es un hueco de cobertura real: si alguien rompe el manejo de errores de esas tres rutas (por ejemplo, quita el `try/catch` o cambia el código de status), ningún test lo detecta. Tampoco hay test para el caso "el MCP devuelve `undefined`/objeto vacío" (p. ej. `details` sin `.events`, `groups` no es array), que sí está parcialmente cubierto por el uso de `?? []` en el código pero no verificado por un test.
**Sugerencia:** Agregar, para cada una de las tres rutas, al menos un test de 502 (mock rechazado) análogo a los que ya existen para las otras rutas, cumpliendo la convención de CLAUDE.md de que toda ruta nueva tenga su test.

## 🔵 Menores

### [M1] Doble mecanismo de rate-limiting con justificación contradictoria
**Archivo:** backend/src/mcp/client.js:29-43 y backend/src/services/sportdb.js:140-148
**Qué pasa:** `mcp/client.js` ahora serializa **todas** las llamadas salientes al MCP con un espaciado mínimo de 350ms (comentario: "serializamos todas las llamadas salientes... en vez de dejar que cada handler golpee el MCP por su cuenta"). Pero `sportdb.js` sigue usando `mapSequential` en `getMatchesByDate`, `findMatchWithLeague` y `listCompetitions` con el comentario "recorrer las 6 ligas en paralelo lo supera [el rate limit] de forma consistente" — como si el throttle de `client.js` no existiera —, mientras que `getRiverBocaMatches` sí usa `Promise.all` sin ese cuidado.
**Cómo falla:** No rompe nada (el throttle global en `client.js` cubre a todos los casos igual), pero el código queda con dos capas de protección de rate-limit que se pisan y comentarios que ya no reflejan la arquitectura real, lo que va a confundir al próximo que lo toque y puede llevar a "arreglar" el rate limit en el lugar equivocado.
**Sugerencia:** Documentar en un solo lugar (el throttle de `client.js`) que esa es la única fuente de verdad para el rate limit, y quitar o actualizar el comentario de `mapSequential` para no sugerir que la secuencialidad ahí es necesaria por rate limiting.

### [M2] `mapMatchStatus` clasifica como "live" cualquier `eventStage` no reconocido, incluyendo estados terminales no confirmados
**Archivo:** backend/src/services/sportdb.js:111-118
**Qué pasa:** El comentario ya documenta la limitación ("SCHEDULED y FINISHED son los únicos valores confirmados; cualquier otra cosa se interpreta como en vivo"), así que es una decisión consciente, pero deja sin cubrir estados como `POSTPONED`, `CANCELLED`, `ABANDONED` o `WALKOVER`, típicos en proveedores tipo Flashscore.
**Cómo falla:** Un partido pospuesto (`eventStage: "POSTPONED"`) se mapea a `status: "live"` con `statusLabel: "POSTPONED"`, y el frontend (que probablemente renderiza un badge "EN VIVO" para `status === "live"`) mostraría como partido en curso uno que ni siquiera se está jugando.
**Sugerencia:** Ya que está documentado como riesgo conocido, al menos agregar un test que fije el comportamiento actual para `eventStage` desconocidos, para que un cambio futuro en el mapeo sea intencional y no accidental.
